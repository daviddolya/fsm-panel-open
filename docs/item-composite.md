# Два локальных изображения в один PNG

Откройте **Уведомления → Два изображения → PNG**. Выберите первое изображение,
второе изображение и **новый** выходной файл с расширением `.png`, затем нажмите
**Создать PNG**. Второе изображение растягивается до размеров первого и помещается
справа. Например, первое изображение 120 × 80 даёт результат 240 × 80.

Подготовка работает без допуска лицензии, в том числе в симуляторе. Она не
скачивает изображения и не отправляет уведомления. Для последующей ручной отправки
откройте вкладку **Telegram** и отдельно выберите сохранённый файл.

При существующем выходном файле выберите новое имя. Исходные изображения не
изменяются. **Отменить** останавливает работу между этапами чтения, декодирования
и кодирования. Уже начатая запись завершается; интерфейс сообщает о сохранении.
Закрытие окна также дожидается принадлежащей ему фоновой работы.

## Поддерживаемые входы и новые ограничения

- Только локальные PNG и JPEG; формат определяется содержимым, а не расширением.
- Один кадр; APNG и другие анимированные входы отклоняются.
- PNG: режимы `1`, `L`, `LA`, `P`, `RGB`, `RGBA`; JPEG: `L`, `RGB`, `CMYK`.
  16-битные изображения и остальные форматы не поддерживаются.
- До 8 МиБ закодированных данных и 4 000 000 пикселей на каждый вход.
  Результат содержит до 8 000 000 пикселей; PNG ограничен 40 МиБ.
- UNC, пути устройств, URL, сетевые диски Windows, ссылки и junction-предки
  отклоняются. Родительские каталоги должны существовать.
- Запись в исходную поставку запрещена: проверяются имена `FSM_PANEL v.*`
  и наличие `Panel.exe` в родительских каталогах.

Эти ограничения — решения новой версии. Они не приписываются оригиналу.
Ошибки API содержат только фиксированный код `image_*`; интерфейс показывает
краткое объяснение без путей, метаданных изображения и исходного текста исключения.
Выбранные пользователем пути остаются видны в полях формы.

## Восстановленный алгоритм

Статическое исследование `Panel.exe`, SHA-256
`3731a48590e3169071b81aab9338a36b38a788133adfd43fada99ad3add1f308`, установило
следующую последовательность в `0x140627380`:

```python
first = Image.open(first_input)
second = Image.open(second_input)
second = second.resize(first.size)
canvas = Image.new("RGBA", (2 * first.width, first.height), (250, 250, 250))
canvas.paste(first, (0, 0))
canvas.paste(second, (first.width, 0))
canvas.save(output, "PNG")
```

Это описание восстановленного поведения, не извлечённый исходный код.
Умножение ширины подтверждено вызовом `0x14062b8dd`, помощником `0x142ce6250`
и его fallback `0x142d17270`.

Новая реализация сохраняет эти операции. Перед `resize` нет преобразования режима;
при `paste` маска не передаётся. Поэтому прозрачность переносится в RGBA, а не
смешивается с фоном. EXIF-поворот не применяется. Метаданные исходных файлов не
переносятся в новый холст.

Зависимость закреплена как **Pillow 12.3.0**, включая `uv.lock`. Проверенный
установленный `PIL/Image.py`, метод `Image.resize`, использует BICUBIC по умолчанию,
а для `1` и `P` — NEAREST. Для `LA` и `RGBA` библиотека сама обрабатывает
предумноженную прозрачность при изменении размера. Эти библиотечные операции
дополнительно не заменяются. См. [официальное описание resize](https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.resize).
Декодированный модуль оригинала `PIL._version` содержит `9.5.0` (constant 6,
offset 65; SHA-256 parsed record
`11e788034bc23ef5b8779d491f1c8b5d967ae0a1ce982897fd3881f72c469db6`).
В [upstream Pillow 9.5.0](https://raw.githubusercontent.com/python-pillow/Pillow/9.5.0/src/PIL/Image.py)
ветви выбора фильтра и предумножения для поддерживаемых режимов совпадают.
Это указание версии в константах и сравнение upstream-кода, а не доказательство
неизменности скомпилированной библиотеки или совпадения пикселей для всех входов.

Оригинал открывал `image0.png` и `image1.png`, а сохранял `image2.png`, который
мог совпасть с третьей скачанной иконкой. Новая версия принимает **два явных входа**
и создаёт только новый файл. Скачивание иконок, автоматическая отправка,
восстановление всего item producer и управление `ITEM_PICTURES_IN_TG` сюда
не входят. Их статус остаётся отдельным от локальной подготовки изображения.

Источники реализации — приватные очищенные контракты; сырые дампы не публикуются:

- `TELEGRAM_SPEC_SANITIZED.md`, SHA-256
  `4743a18227969065aa9537718dbe8b13560f275ae656786023d8ef0a8178a349`.
- `ITEM_COMPOSITE_ADDENDUM_SANITIZED.md`, SHA-256
  `184b6f45bd3dc6dc338fcc159343468fbacc9f42300a3a80f37310453db7726c`.

## API и владение работой

`fsm_panel.notifications.images` предоставляет:

```python
from pathlib import Path
from fsm_panel.notifications.images import compose_item_image_files

result = compose_item_image_files(
    Path("first.png"), Path("second.jpg"), Path("new-composite.png")
)
print(result.width, result.height)
```

`compose_item_images(first: bytes, second: bytes, *, cancelled=None)` возвращает
`ItemComposite(png, width, height)` без файловых операций. `png` исключён из `repr`.
Файловый вариант возвращает такой же результат после успешной записи.
Оба принимают необязательный `threading.Event` для кооперативной отмены и
выбрасывают `ItemCompositeError` с фиксированным `.code`.

Файловая обёртка ограничивает чтение, проверяет идентичность и состояние открытого
источника, затем повторно проверяет родителей выходного пути. PNG полностью
кодируется в памяти до открытия назначения в режиме `xb`. Конкурентные обычные
создатели не заменяют победивший файл. После начала записи отмена не прерывает
`write`/`flush`/`fsync`. При обычной ошибке удаляется только созданный этой операцией
файл с совпадающей идентичностью. Ошибка очистки сообщается отдельно.

Это не транзакционная защита от враждебной подмены каталогов другим процессом.
При аварийном завершении процесса или отключении питания может остаться неполный
новый PNG; его нужно проверить и удалить вручную. Существующие файлы никогда
не открываются для перезаписи.

GUI использует `AsyncBridge` и отдельную рабочую задачу `asyncio.to_thread`.
Результаты передаются Qt-сигналами. Завершение фоновой задачи хранится отдельно
от отменяемого вызывающим кодом Future моста. Отмена Future или ожидания закрытия
не освобождает владение продолжающейся записью. Лицензирование и Telegram-клиент
не вызываются.

## Проверка

```powershell
uv sync --frozen --group dev
uv run pytest tests/notifications/test_images.py tests/ui/test_item_composite.py tests/ui/test_notifications.py tests/qa/test_notification_ui_boundaries.py -q
```

Тесты используют только синтетические изображения. Проверяются точные RGBA-пиксели,
разные размеры, BICUBIC/NEAREST, палитра, прозрачность, EXIF, ограничения,
ошибки записи, конкурентное создание, отзыв/отсутствие допуска и жизненный цикл GUI.
Это проверка локальной реконструкции; оригинал и реальные Steam/Telegram-сервисы
не запускались. Паритет с оригиналом на стенде не подтверждён.
